# Releasing

## Version and build number

`app.json` carries two separate things, and they move independently:

| Field | What it is | Who reads it | When it changes |
|---|---|---|---|
| `expo.version` | The version people see, e.g. `1.2.0` | Users, release notes | When the release is meant to look different to a user |
| `expo.android.versionCode` / `expo.ios.buildNumber` | The build's identity | Google Play, App Store Connect | Every build that is uploaded, without exception |

Both stores refuse an upload whose build number they have already seen, so the number has to
go up every time. It is one number for both platforms: `ios.buildNumber` is always the string
form of `android.versionCode`, and a test (`scripts/__tests__/build-number.test.ts`) fails if
they drift apart.

`ios/` and `android/` are generated by `expo prebuild` and are not tracked, so `app.json` is the
only place these values live. Do not edit them in Xcode or `build.gradle`; prebuild overwrites both.

## How the build number advances

It is bumped in the release commit:

```sh
npm run bump-build
```

That increments both fields together and leaves `expo.version` alone. Commit the result as part
of the release, so the number in the store always matches a commit on `main`.

Taking it from the CI run number instead was considered and not chosen for now. CI does not build
release artefacts today, and a number assigned outside the repository cannot be traced back to
the commit that produced it. Revisit this if releases move to CI or EAS Build.
