# Copy and i18n: what is translated, and what is not

This app translates some of its copy and not the rest, on purpose. This document says
which, why, and how the line is enforced, because until now the rule existed only in an
untracked agent-guidance file and the code did not follow it.

## The problem this settles

The standing rule was that no new hardcoded user-facing string should be added. The code
disagreed with it, comprehensively. At the point this was written:

- `services/i18n.ts` held 53 keys, with 81 `t()` call sites.
- `app/`, `components/` and `view-models/` held roughly **258** hardcoded user-facing
  strings, with another ~50 in `models/` fixture data that screens render.
- Six of 23 screens used i18n at all. Seventeen were entirely hardcoded, including three of
  the four tabs.

So coverage was around 21%, and the rule was unenforceable in practice. Following it inside
a screen where nothing else was translated produced a file with three keys and thirty
literals, which serves a translator worse than either consistent choice. The disagreement
was resolved ad hoc every time somebody added a line of copy.

## The decision

**i18n covers the copy a user meets when something is going wrong, or when they are
connecting a phone to a Pond.** Concretely: connection state, pairing, remote access,
trust, and the errors arising from those.

Everything else is English until a second locale is actually on the roadmap.

This is not a retreat from a standard that was being met. It is a description of what the
catalogue already was: every one of those 81 call sites was connection, pairing,
remote-access or trust copy, and the only mention of i18n in tracked documentation
(`docs/PINNED_HTTPS.md`) already described that narrow scope. Migrating the remaining ~300
strings would mostly mean translating copy on screens that are UI scaffold, not yet wired
to any backend, and which will be rewritten when they are.

The alternative remains open. If a second locale is ever real, the honest path is to
migrate screen by screen and widen the enforced surface below as each one lands.

## What is enforced

`eslint.config.js` applies `i18next/no-literal-string` as an **error**, scoped by `files`
to the covered surface:

- `**/pond-pairing.tsx`
- `**/remote-access.tsx`
- `**/connect-desktop.tsx`
- `components/patterns/connection-status.tsx`
- `components/patterns/remote-access-offer.tsx`

A bare user-facing string in one of these fails the build. That is the point: a rule nobody
can accidentally break is worth more than a convention everybody means to follow.

### How the rule is tuned, and why

- `mode: 'jsx-only'` rather than `jsx-text-only`, because copy hides in expression
  containers — `{matter ? t('commission.type') : 'Enter the code instead'}` is exactly the
  shape the narrower mode misses.
- `jsx-attributes.include` lists only attributes that render as copy. Unrestricted, the
  rule also flags `variant="primary"` and `name="camera"`, and a rule that cries wolf is a
  rule somebody switches off.
- `words.exclude` drops URLs, `sha256/` prefixes and any string with no letters in it —
  format examples and separators a translator would leave exactly as they are.

  One trap worth knowing if you edit these patterns: the plugin wraps each in `^…$` for a
  whole-string match, so a leading `^` produces `^^…$` and silently matches nothing. The
  trailing `.*` is load-bearing.

### What the rule does not catch

It is a lint rule over literals, so it sees only what is written as a literal in a covered
file. It does not see copy composed at runtime, and `app/(stack)/logs.tsx` shows the shape:
tab labels built as `tab.charAt(0).toUpperCase() + tab.slice(1)` are untranslatable by
construction and invisible to any literal-based rule.

Service and model files in the covered area — `services/remote-access.ts`,
`services/pond-trust.ts`, `models/pairing.ts` — are covered by this convention but **not**
by the lint rule, which is only meaningful over JSX. They contain no hardcoded copy today.

## Deliberately outside the enforced surface

Three files use the catalogue but are not enforced, because they mix covered copy with copy
that is not:

| File | Why |
|---|---|
| `app/(tabs)/profile.tsx` | Sign-out copy is covered; the profile menu labels around it are not |
| `app/(stack)/developer.tsx` | Developer tooling, not user-facing product copy |
| `app/(stack)/commission-device.tsx` | The `commission` keys are covered; the rest of the Matter flow is not |

Enforcing on these would pull unrelated copy into the rule by accident, which is the muddle
this document exists to end. They keep their existing keys, and new connection or error copy
in them should still use one.

## Adding copy

- **In a covered file**: add a key to `services/i18n.ts` and use it. The lint rule will tell
  you if you forget.
- **Anywhere else**: a plain string is correct. Do not add a lone key to an otherwise
  untranslated screen — that is the half-migrated state this replaced.
- **New connection, pairing, remote-access or trust copy**, wherever it lives, belongs in
  the catalogue.

`services/__tests__/i18n.test.ts` reads every `t('…')` call site out of the source and
asserts each key resolves. This matters because i18next answers a missing key with the key
itself, so a deleted key does not throw — it ships, and a user sees `pairing.codeTitle`
where a sentence should be.

The test does not check the reverse direction. An unused key is dead weight but harmless,
and keys can be selected dynamically, so flagging them would produce false alarms.
